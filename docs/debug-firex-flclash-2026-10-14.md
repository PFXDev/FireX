## 修复结论

- CF XHTTP：某些候选入口在保持原 SNI / HTTP Host 时返回 HTTP 403 / Cloudflare 1034。原始域名的真实代理请求通过，后续候选入口通过端到端测试后，仅更新目标节点的公开连接地址，并验证其余参数不变。
- REALITY：原握手目标一度不可达。隔离实例只调整握手目标与 SNI，保留原有密钥、VLESS Encryption、Vision 和附加签名，端到端请求通过。应用前后检查配置预览、下发结果和读回数据。
- FireX 原先丢弃分享链接明确携带的 `support-x25519mlkem768=true`，导致 mihomo 的 REALITY 认证失败。现在解析并生成 `reality-opts.support-x25519mlkem768: true`；缺省或 false 的链接继续使用原行为。
- 重新编译 FireX 并同步客户端订阅后，通过独立测试内核和客户端延迟测试验证。单次延迟测试不代表持续吞吐性能。

## CF 候选入口复核方法

- 始终保持订阅节点原 SNI / HTTP Host，分别验证 TLS、域名回源响应和实际 XHTTP 代理请求。
- [Cloudflare 官方说明](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1034/)将 1034 定义为 **Edge IP Restricted**。TLS 握手成功或延迟低不能证明可回源。
- 对照测试使用独立节点副本，关闭临时内核的 TUN / 内置 DNS，并绑定物理网卡。
- 用 HTTP 204 请求验证端到端可达性，再用完整下载验证 HTTP 状态、实际收到的字节数和耗时。
- 更新目标节点前后读回配置，确认仅预期字段和更新时间变化，并检查生成订阅中的地址、端口、SNI 与 XHTTP 参数。
- 原握手目标恢复 HTTPS 可达，只证明当时 HTTPS 恢复，不能替代 REALITY 端到端验证。
